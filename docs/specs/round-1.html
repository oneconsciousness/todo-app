Solution diagram

One origin, two API replicas, one database

The browser only ever talks to web on port 8080. Nginx serves the built SPA and forwards /api/* to the API, so the app and the API share one origin: no CORS, and the session cookie stays first-party. Running two API replicas already in round 1 proves the backend keeps no state in memory, one round before Kubernetes depends on it.

High-level choices

Decisions

Locked ones come from the kickoff or follow directly from it. The rest are recommendations for you to confirm.

D1

Stack

locked
Choice
Backend: Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2 async with asyncpg, alembic, uv, ruff, mypy strict. Frontend: React 19, Vite, TypeScript strict, React Router, TanStack Query 5, Zod, Tailwind 4, dnd-kit, ESLint and Prettier, npm.
Instead of
Node and Express, which the brief gives as an example.
Why
Typed models at every boundary on both sides, native async, and an OpenAPI document for free. TanStack Query is the high-level async layer the brief asks for on the frontend.
D2

Storage is PostgreSQL from day one

locked
Choice
Postgres 17 in a container with a named volume. The same engine runs as a StatefulSet in round 2 and as Azure Database for PostgreSQL in round 3.
Instead of
In-memory or file storage, or SQLite.
Why
Several replicas must share one store, and transactions plus constraints keep reorder and ownership correct. Integration tests run on the same engine as production, so they test what ships.
D3

Accounts: open sign-up and sign-in by email

your call
Choice
The landing page is sign-in, with a link to create an account (email and password, 12 to 128 characters). Passwords are hashed with argon2id, off the event loop.
Instead of
Seeded demo users only, or a third-party login.
Why
A reviewer can make two accounts and see that each one only sees its own tasks. Nothing to configure, and no outside service.
Costs
No email verification or password reset in round 1; both go on the "more time" list.
D4

Session: a signed token in an httpOnly cookie

your call
Choice
On sign-in the API sets a JWT (HS256, 8-hour lifetime) as cookie session: HttpOnly, SameSite=Strict, Path=/api, Secure once TLS exists in rounds 2 and 3. Sign-out clears it. Any replica can verify it with the shared secret.
Instead of
A bearer token in localStorage, which any injected script can read. Or a sessions table, which can be revoked but adds a lookup per request.
Why
Stateless across replicas and out of reach of page scripts. CSRF is covered by SameSite=Strict, the single origin, JSON-only request bodies and an Origin check on every write.
Costs
A token can't be revoked before it expires. Refresh-token rotation with a deny list is the round 3 hardening item.
D5

Ids are UUIDs

locked
Choice
Users and tasks use UUID primary keys generated by the API.
Instead of
Serial integers.
Why
Ids can't be guessed or counted, and any replica can mint one without asking the database first.
D6

Ordering by fractional ranks

your call
Choice
Each task has a rank string, and the list is sorted by rank. A move computes a new rank between its new neighbours, so it changes one row. New tasks go to the top. Reordering is turned off while a search is active, because moving within a filtered subset is ambiguous.
Instead of
Integer positions renumbered on every move, or gapped integers with occasional rebalancing.
Why
One write per move whatever the list size, no renumbering, and the rank maths is a pure function we can test with generated inputs (see the figure below).
Costs
Ranks get longer when many tasks are dropped into the same gap. In practice that's a character or so per move into one spot; a rebalancing job goes on the "more time" list.
D7

Search runs on the server

your call
Choice
GET /api/v1/tasks?q= matches a case-insensitive substring in title or notes, keeps rank order, and is backed by a trigram index. The search box waits 250 ms after typing stops and keeps showing the previous results while the next ones load.
Instead of
Filtering the loaded list in the browser.
Why
The API owns operations on the data, the index keeps search fast as lists grow, and paging can come later without changing how search behaves.
D8

Task fields

your call
Choice
Title (required, 1 to 200 characters), notes (up to 5,000), completed, optional due date, created and updated times.
Instead of
Also priority, tags or subtasks.
Why
That's enough to make the detail screen worth opening, and every field gets tested end to end. More fields would add surface without showing anything new.
D9

HTTP contract

locked
Choice
Resources under /api/v1. Success: 200, 201 with a Location header, 204. Errors: 400 for validation (FastAPI's 422 is remapped), 401 when the session is missing or bad, 403 when a write comes from another origin, 404 for a missing task or one owned by someone else, 409 when an email is already registered. One error body shape: {"error": {"code", "message", "details"}}.
Why
Follows the brief's status-code hint. Every code has a reason the frontend can act on. Answering 404 for other users' tasks means the API never confirms that someone else's id exists.
D10

Two API replicas already in round 1

your call
Choice
Compose runs api with two replicas, and nginx round-robins between them. Each response carries an X-Served-By header with the replica's hostname.
Instead of
One replica until round 2.
Why
A live test can show that a session issued by one replica works on the other. Any accidental in-memory state shows up in round 1, where it's cheap to fix. The header also helps trace requests in Kubernetes.
D11

Logs for monitoring

locked
Choice
API logs are JSON lines on stdout. Each request gets one access line (request_id, user_id, method, route, status, duration_ms), plus a startup "ready" line and every caught error with context. X-Request-ID is accepted from the caller or created, and echoed back. /healthz and /readyz are the probes. In the SPA: console.info when it boots, and console.error from the error boundary and the global query error handler.
Why
Your logging guidance: every line helps someone watching the system, and Kubernetes and Azure pick up stdout as is.
D12

Coverage floors

your call
Choice
CI fails below 90% line and branch coverage on the backend and 85% on the frontend. These are floors on tests that assert something, not targets to pad.
Why
High enough that a missed branch shows up, low enough that nobody writes a pointless test just to cover glue code.
D6 in one picture

A move writes one row

Moving “Buy milk” from the bottom to just below “Call Sam”. With integer positions, every task between the old and new place is renumbered. With ranks, only the moved task gets a new key, halfway between its new neighbours. Ranks compare byte by byte, so the column uses the "C" collation; a locale-aware collation would sort a0V in the wrong place.

How a request moves

Functional core, imperative shell

Everything that touches the network or the database sits at the edges and stays thin. The rules (rank maths, the search pattern, applying a partial update, mapping rows to responses) are pure functions that never mutate their input, in a core that the unit tests reach directly. FastAPI's Depends composes each request from small providers. Errors are raised as domain exceptions and turned into HTTP status codes in one place.

Exit criteria

Round 1 is done when

It works

  • On a clean Mac, docker compose up --build brings up the stack and localhost:8080 lets a new user sign up and use every feature.
  • Two users never see each other's tasks, through the UI or the API.
  • The layout holds at phone width and at desktop width.

It's proven

  • All five test layers are green and above the coverage floors; you've reviewed the code.
  • CI runs hygiene, backend, frontend and end-to-end jobs once the GitHub remote exists.
  • The README covers running round 1 on a Mac.

Delivery: after the plan and the instructions walkthrough, round 1 is four PRs, each reviewed by you: the coding plan, the backend API, the frontend, then containers with the live and browser tests. Waits outside our control: about 2 minutes of CI per push, plus your review of each PR.
