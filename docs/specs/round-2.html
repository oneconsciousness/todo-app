Solution diagram

One front door, three API pods on three nodes, one database

The browser talks to https://localhost:8443. k3s's built-in Traefik ends TLS and sends every request to the web pods. nginx in those pods does exactly what it does in compose: serves the SPA, sets the security headers and forwards /api/*. It reaches the API through a headless Service, which lists each pod, so every request is balanced across the three pods rather than pinned to one.

High-level choices

Decisions

Numbering continues from round 1 (D1 to D20). Locked ones follow from documents you already signed off. The calls in revision 1 were my recommendations; the lead's answers are recorded under Sign-off.

D21

A three-node k3d cluster

locked
Choice
k3d 5.9.0 running k3s v1.36.4, one server and two agent nodes, from a config file at deploy/k3d/cluster.yaml. Port 8443 on the Mac maps to 443 on the cluster's load balancer. The three API pods are spread one per node.
Instead of
One node, which is lighter but puts every replica on one machine.
Why
Pods on different nodes talk over the cluster network, as they will on AKS. A node going away is something we can show, not only describe.
Costs
About 1.5 GB more of Docker's memory. Docker has 8 GB here, which is enough.
Found
k3d's own load balancer allows 1,024 connections by default and dropped them past about 500 users. The cluster config raises it to 8,192.
D22

One Kustomize base, one overlay per target

locked
Choice
deploy/base/ holds every resource once. deploy/overlays/k3d/ sets what differs locally: hostname, TLS secret name, image tags, sizes. Round 3 adds deploy/overlays/aks/.
Instead of
A Helm chart, or copied manifests per environment.
Why
Plain YAML you can read line by line, and kubectl builds it with no extra tool. The deployment rule asks for this shape.
D23

The same images, tagged with the commit

locked
Choice
The compose build makes todo-api:<sha> and todo-web:<sha>; k3d image import copies them onto every node. Pods never pull, so no registry is needed in round 2.
Instead of
A local registry, or images built separately for the cluster.
Why
What passed in compose is exactly what runs in k3d. Round 3 pushes the same images to Azure Container Registry.
D24

Postgres as a one-pod StatefulSet

locked
Choice
The same Postgres 18.6 image as compose, one pod with a volume from k3s's local-path storage.
Instead of
A Postgres operator with replicas and backups, such as CloudNativePG.
Why
Round 3 uses Azure's managed Postgres, which brings its own replicas and backups. An operator here would be built once and thrown away.
Costs
The database is a single pod. Losing its node loses the service until it comes back; the data survives on the volume.
D25

Migrations run as a Job, before the API rolls out

locked
Choice
A Job named migrate-<sha> runs alembic upgrade head with the API image and the database address alone. The deploy waits for it to complete, then rolls out the API.
Instead of
Running migrations at start-up in every pod, or in an init container.
Why
One run per release, never three pods racing to migrate. A failed migration stops the release before any pod changes.
D26

Three API pods that roll without dropping a request

locked
Choice
A Deployment that starts with 3 replicas, one uvicorn process each; the autoscaler in D34 takes it to 5 under load. A rolling update adds a new pod before removing an old one, and a disruption budget keeps at least 2 serving. CPU and memory requests and limits are set; the CPU limit is one core, the most one uvicorn process can use. Probes: /livez for liveness, /readyz for readiness.
Instead of
More uvicorn workers per pod, which hides failures inside one pod and splits the connection budget unevenly.
Why
The round 1 spec planned 3 replicas and a budget of 45 connections for round 2. Scaling stays a replica count.
D27

nginx stays the front of the app; Traefik only ends TLS

locked
Choice
One Ingress sends everything to the web Service (2 nginx pods). nginx forwards /api/* to a headless API Service and re-reads its pod list from DNS, as it does in compose. The nginx image reads the DNS server and the API's address from its environment at start-up, through the image's own template step, so one image runs in both places.
Instead of
Traefik routing /api straight to the API. That needs the security headers, CSP, body limit and request id written a second time as Traefik middleware, and compose and k3d would no longer run the same front end. Or a normal Service, where nginx's kept-alive connections stick to one pod: the load skews and a rollout drains slowly.
Why
One nginx config, already tested by every suite, guards the app in all three rounds.
Costs
nginx learns about pod changes through DNS, up to about 15 seconds late. D29 covers that.
D28

TLS on k3d with a locally trusted certificate

locked
Choice
mkcert makes a certificate for localhost that this Mac trusts. You create it and load it as a TLS Secret. The cookie turns Secure, which the app allows only with a real JWT secret, never the example one.
Instead of
Traefik's own self-signed certificate: no setup, but the browser warns and the tests must skip certificate checks. Or plain HTTP until AKS: the simplest, but the Secure cookie, HTTPS origin and TLS ending would first be tried on Azure.
Why
The round 1 spec turns the cookie Secure once TLS exists. Rehearsing that locally finds a broken sign-in here rather than on AKS.
Costs
One brew install mkcert and mkcert -install, which adds a local certificate authority to the Mac's trust store. That is your step, and a reviewer's too.
D29

A pod leaves the rotation before it stops

locked
Choice
Each API pod has a 20-second preStop sleep, using Kubernetes's built-in sleep action so no shell is needed. Then uvicorn gets SIGTERM and finishes in-flight requests within its existing 20-second limit. The grace period is 45 seconds. The deployment rule's line "/readyz fails once shutdown starts" is replaced by this.
Instead of
Making /readyz fail after SIGTERM. Kubernetes already takes a terminating pod out of the Service the moment shutdown starts, so a failing probe adds nothing. The gap is DNS: nginx can keep sending to the pod for up to about 15 seconds, and only the sleep covers that.
Why
A rolling update or a killed pod should fail no requests. The timeline below shows why 20 seconds is enough.
D30

Settings in a ConfigMap; secrets you create

locked
Choice
A ConfigMap holds the origin, the cookie flag and the log level. Two Secrets hold the database password with the JWT secret, and the TLS certificate. The deploy script creates them on the first deploy, unless they already exist: random values for the first, a mkcert certificate for the second. Nothing is printed, kept on disk or committed. To use your own values, create the Secrets first with the commands in the README. The pod builds DATABASE_URL from the password at start, so the password is stored once.
Instead of
Secrets committed in any form, including encrypted ones.
Why
The kickoff and the deployment rule: secrets are never in the repo, and I never see them. Round 3 moves them to Key Vault.
Changed
Revision 1 had you type the commands. The lead asked for round 2 to be finished while away, so the script creates the Secrets instead; the values stay unseen. Your call on return.
D31

Kubernetes's defaults for Pod Security and the network, for now

deferred
Choice
No Pod Security level on the namespace and no network policies yet. Each container still runs as a non-root user with a read-only filesystem and no capabilities, as the deployment rule asks and as in compose.
Instead of
The restricted Pod Security level and default-deny network policies, which revision 1 recommended.
Why
The lead's call: defaults for now. Both are in FUTURE.md.
Costs
Any pod in the cluster can reach Postgres. Only our pods run there.
D32

One deploy script, and every apply still asks you

locked
Choice
deploy/k3d/deploy.py (Python standard library) runs the order below for the README and CI. In this session I run the same steps one at a time, so each kubectl apply and delete asks you first, as the guard intends.
Instead of
Me running the script in the session, which would apply manifests without asking you for each one.
Why
A reviewer gets one command, and you keep the say over every change to a running cluster.
D33

k3d runs on the Mac only

deferred
Choice
CI keeps its round 1 jobs. The k3d suites and disruption runs are run on this Mac and their results recorded.
Instead of
A k3d job on every PR, which revision 1 recommended.
Why
The lead's call: local Mac only. A k3d CI job is in FUTURE.md.
Costs
A change that breaks the cluster but not compose is caught only when someone runs it on k3d.
D34

The API scales itself between three and five pods

locked
Choice
A HorizontalPodAutoscaler on the API: at least 3 pods, at most 5. It adds a pod when the pods average over 70% of their CPU request, at once, and removes one only after two quiet minutes. It reads CPU from the metrics server k3s ships.
Instead of
A fixed 3 pods, scaled by hand, which revision 2 had and which left the autoscaler to round 3.
Why
The lead's call: "yes, add the autoscaler in round 2. Its critical." Kubernetes should follow the load, and k3d can prove it does.
Costs
Five is the ceiling: each pod opens up to 15 database connections, and 6 pods would pass 80% of Postgres's 100. Going higher needs a connection pooler in front of Postgres, which Azure's managed Postgres brings in round 3. Postgres itself stays one pod; a database grows by replication, not by copies of the pod.
Why D29 works

A pod leaves the rotation before it stops

When a pod is deleted, by a rolling update or by hand, Kubernetes removes it from the Service at once. nginx still holds the old pod list for up to about 15 seconds: its own 10-second re-read plus the cluster DNS's 5-second record lifetime. The pod keeps serving through that window, then drains.

Looking ahead

What round 3 changes

The base manifests stay. The AKS overlay swaps Postgres for Azure Database for PostgreSQL (with its built-in PgBouncer, so the autoscaler can go past five pods), uses the cluster's managed ingress with a real certificate, pulls images from Azure Container Registry and reads secrets from Key Vault. GitHub Actions deploys it after signing in to Azure with OIDC, with no stored keys. You run or approve everything that touches Azure.

Exit criteria

Round 2 is done when

  • On a Mac with Docker Desktop and k3d, the README's steps create the cluster and deploy it. https://localhost:8443 serves the app, and the three API pods run on three different nodes.
  • The cluster runs the same commit-tagged images as compose, from one Kustomize base and a k3d overlay. You reviewed every manifest before it was first applied.
  • The migration Job completes before the API rolls out, and deploying the same commit again changes nothing.
  • The live and browser suites pass against k3d, and still pass against compose.
  • Under 200 users, deleting an API pod, a rolling restart and replacing every pod cause no failed request and no lost data; signed-in users stay signed in.
  • No secret is in the repo, and no secret value is printed by any step.
  • Under rising load the autoscaler adds API pods, up to 5, and removes them when the load falls, with no failed request.
  • The round's capacity figure on k3d is recorded next to round 1's.
  • CI's round 1 jobs stay green.
  • The README has clear steps for setting up and running on k3d, which the lead can follow to try the app.
