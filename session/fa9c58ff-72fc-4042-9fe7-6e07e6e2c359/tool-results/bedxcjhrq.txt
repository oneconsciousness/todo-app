    Solution diagram
    One origin, two API replicas, one database
    The browser only ever talks to web on port 8080. Nginx serves the built SPA and forwards /api/* to the API, so the app and the API share one origin: no CORS, and the session cookie stays first-party. Running two API replicas already in round 1 proves the backend keeps no state in memory, one round before Kubernetes depends on it.
        [svg]
      Round 1 runs four services. migrate uses the API image and must exit successfully before either replica starts, so no replica serves an old schema and replicas never race to migrate. The tests go through the same front door a user does.
    High-level choices
    Decisions
    Locked ones come from the kickoff or follow directly from it. The rest are recommendations for you to confirm.
      D1
        Stack
locked
          ChoiceBackend: Python 3.13, FastAPI, Pydantic v2, SQLAlchemy 2 async with asyncpg, alembic, uv, ruff, mypy strict. Frontend: React 19, Vite, TypeScript strict, React Router, TanStack Query 5, Zod, Tailwind 4, dnd-kit, ESLint and Prettier, npm.
          Instead ofNode and Express, which the brief gives as an example.
          WhyTyped models at every boundary on both sides, native async, and an OpenAPI document for free. TanStack Query is the high-level async layer the brief asks for on the frontend.
      D2
        Storage is PostgreSQL from day one
locked
          ChoicePostgres 17 in a container with a named volume. The same engine runs as a StatefulSet in round 2 and as Azure Database for PostgreSQL in round 3.
          Instead ofIn-memory or file storage, or SQLite.
          WhySeveral replicas must share one store, and transactions plus constraints keep reorder and ownership correct. Integration tests run on the same engine as production, so they test what ships.
      D3
        Accounts: open sign-up and sign-in by email
locked
          ChoiceThe landing page is sign-in, with a link to create an account (email and password, 12 to 128 characters). Passwords are hashed with argon2id, off the event loop.
          Instead ofSeeded demo users only, or a third-party login.
          WhyA reviewer can make two accounts and see that each one only sees its own tasks. Nothing to configure, and no outside service.
          CostsNo email verification or password reset in round 1; both are in FUTURE.md.
          AlsoReviewers can script bulk tests against the API: the OpenAPI document and interactive docs are served at /api/docs.
      D4
        Session: a signed token in an httpOnly cookie
locked
          ChoiceOn sign-in the API sets a JWT (HS256, 8-hour lifetime) as cookie session: HttpOnly, SameSite=Strict, Path=/api, Secure once TLS exists in rounds 2 and 3. Sign-out clears it. Any replica can verify it with the shared secret.
          Instead ofA bearer token in localStorage, which any injected script can read. Or a sessions table, which can be revoked but adds a lookup per request.
          WhyStateless across replicas and out of reach of page scripts. CSRF is covered by SameSite=Strict, the single origin, JSON-only request bodies and an Origin check on every write.
          CostsA token can't be revoked before it expires. Refresh-token rotation with a deny list is the round 3 hardening item.
          LaterSign-in with Microsoft, Google or Apple (OpenID Connect), chosen per client. Recorded in FUTURE.md.
      D5
        Ids are UUIDs
locked
          ChoiceUsers and tasks use UUID primary keys generated by the API.
          Instead ofSerial integers.
          WhyIds can't be guessed or counted, and any replica can mint one without asking the database first.
      D6
        Ordering by fractional ranks
locked
          ChoiceEach task has a rank string, and the list is sorted by rank. A move computes a new rank between its new neighbours, so it changes one row. New tasks go to the top. Reordering is turned off while a search is active, because moving within a filtered subset is ambiguous.
          Instead ofInteger positions renumbered on every move, or gapped integers with occasional rebalancing.
          WhyOne write per move whatever the list size, no renumbering, and the rank maths is a pure function we can test with generated inputs (see the figure below).
          CostsRanks get longer when many tasks are dropped into the same gap. In practice that's a character or so per move into one spot; a rebalancing job goes on the "more time" list.
      D7
        Search runs on the server
locked
          ChoiceGET /api/v1/tasks?q= matches a case-insensitive substring in title or notes, keeps rank order, and is backed by a trigram index. The search box waits 250 ms after typing stops and keeps showing the previous results while the next ones load.
          Instead ofFiltering the loaded list in the browser.
          WhyThe API owns operations on the data, the index keeps search fast as lists grow, and paging can come later without changing how search behaves.
      D8
        Task fields
locked
          ChoiceTitle (required, 1 to 200 characters), notes (up to 5,000), completed, optional due date, created and updated times.
          Instead ofAlso priority, tags or subtasks.
          WhyThat's enough to make the detail screen worth opening, and every field gets tested end to end. More fields would add surface without showing anything new.
          LaterOnce everything works: create and update tasks by describing them in text or voice, and an AI-written summary home page, possibly over the AG-UI protocol. Recorded in FUTURE.md.
      D9
        HTTP contract
locked
          ChoiceResources under /api/v1. Success: 200, 201 with a Location header, 204. Errors: 400 for validation (FastAPI's 422 is remapped), 401 when the session is missing or bad, 403 when a write comes from another origin, 404 for a missing task or one owned by someone else, 409 when an email is already registered, 412 when an edit is based on an old version (D17), 503 when the API is overloaded or the database is unreachable (D13, D15). One error body shape: {"error": {"code", "message", "details"}}.
          WhyFollows the brief's status-code hint. Every code has a reason the frontend can act on. Answering 404 for other users' tasks means the API never confirms that someone else's id exists.
      D10
        Two API replicas already in round 1
locked
          ChoiceCompose runs api with two replicas, and nginx round-robins between them. Each response carries an X-Served-By header with the replica's hostname.
          Instead ofOne replica until round 2.
          WhyA live test can show that a session issued by one replica works on the other. Any accidental in-memory state shows up in round 1, where it's cheap to fix. The header also helps trace requests in Kubernetes.
      D11
        Logs for monitoring
locked
          ChoiceAPI logs are JSON lines on stdout. Each request gets one access line (request_id, user_id, method, route, status, duration_ms), plus a startup "ready" line and every caught error with context. X-Request-ID is accepted from the caller or created, and echoed back. /livez and /readyz are the probes (D19). In the SPA: console.info when it boots, and console.error from the error boundary and the global query error handler.
          WhyYour logging guidance: every line helps someone watching the system, and Kubernetes and Azure pick up stdout as is.
      D12
        Coverage floors
locked
          ChoiceCI fails below 90% line and branch coverage on the backend and 85% on the frontend. These are floors on tests that assert something, not targets to pad.
          WhyHigh enough that a missed branch shows up, low enough that nobody writes a pointless test just to cover glue code.
    D6 in one picture
    A move writes one row
    Moving “Buy milk” from the bottom to just below “Call Sam”. With integer positions, every task between the old and new place is renumbered. With ranks, only the moved task gets a new key, halfway between its new neighbours. Ranks compare byte by byte, so the column uses the "C" collation; a locale-aware collation would sort a0V in the wrong place.
        [svg]
      The API takes PUT /api/v1/tasks/{id}/position with {"after_id": … | null}. The server looks up the neighbours itself, inside one transaction, so a client with a stale view can't put a task between two tasks that are no longer next to each other.
    How a request moves
    Functional core, imperative shell
    Everything that touches the network or the database sits at the edges and stays thin. The rules (rank maths, the search pattern, applying a partial update, mapping rows to responses) are pure functions that never mutate their input, in a core that the unit tests reach directly. FastAPI's Depends composes each request from small providers. Errors are raised as domain exceptions and turned into HTTP status codes in one place.
        [svg]
      The shaded box is the only place business rules live, and nothing in it does I/O. Every repository query filters on owner_id, so ownership is enforced in the SQL itself, not checked after a row is loaded.
    Many users at once · FastAPI and uvicorn
    Async and concurrency
    Each API replica is one uvicorn process running one event loop. The loop can hold thousands of open requests, but only while each of them is waiting on I/O. Anything that keeps the loop busy (a slow hash, a blocking call, a synchronous write) stalls every request on that replica at once. So the design has three jobs: never block the loop, put a limit on every shared resource, and when a limit is reached, make requests queue for a bounded time or get a clear 503 rather than pile up.
        [svg]
      Everything the loop hands off has a limit: 200 requests in progress per replica, 15 database connections, 4 hashes at a time. When a limit is reached, requests wait for a bounded time; past that wait the client gets a 503 with the error envelope, never a hung connection.
      D13
        One uvicorn process per container, every handler async
locked
          Choiceuvicorn[standard] (uvloop, httptools) with one worker per container; more capacity means more replicas. Every route is async def and uses only async libraries. --limit-concurrency 200 answers 503 past 200 in-flight requests. --timeout-graceful-shutdown 20 lets in-flight requests finish on SIGTERM, then the lifespan closes the pool. Nginx keeps connections to the API open and caps request bodies at 64 KB.
          Instead ofGunicorn or uvicorn managing several worker processes inside one container. Or plain def handlers, which FastAPI runs on a thread pool capped at 40 threads by default.
          WhyOne process per container lets Docker and Kubernetes restart it, count it and scale it, and each pod's memory and CPU stay predictable. Async-only handlers mean the loop is the only scheduler to reason about.
      D14
        Password hashing runs off the loop, at most four at a time
locked
          Choiceargon2id with OWASP's parameters (19 MiB memory, 2 passes, 1 lane), run through asyncio.to_thread behind an asyncio.Semaphore(4) per process. argon2-cffi releases the GIL while it hashes, so the hashes really do run in parallel with the loop.
          Instead ofHashing on the loop, or without a limit.
          WhyOne hash takes tens of milliseconds of CPU. On the loop, every sign-in would freeze that replica for that long. Without a limit, a burst of sign-ins would exhaust memory: the library's default profile uses 64 MiB per hash, so 100 sign-ins at once would need over 6 GB. With the semaphore, extra sign-ins wait their turn instead.
      D15
        A connection budget, and timeouts on every wait
locked
          ChoiceAsync SQLAlchemy on asyncpg. Each replica has a pool of 10 connections plus 5 overflow, a 5-second wait for a free one, and pool_pre_ping. Postgres runs with statement_timeout 5 s and idle_in_transaction_session_timeout 10 s. Each request gets its own AsyncSession and one transaction, committed on success and rolled back on any exception. Sessions are never shared between concurrent coroutines, because an AsyncSession isn't safe for that.
          BudgetTotal connections = replicas × 15, kept under 80% of Postgres's 100. That's 30 in round 1 and 45 in round 2. Round 3 adds autoscaling, so it puts the PgBouncer built into Azure's Postgres in front.
          WhyRequests are short, so 15 connections serve many concurrent users. When load exceeds that, requests wait up to 5 seconds and then get a clear 503, rather than an unbounded queue taking down the database.
          ReportedThe final report states, for each round, how many concurrent users the stack served within budget, measured by D18 rather than estimated.
    Many requests touching the same rows
    Races and consistency
    Tasks are private, so two different users never contend for the same row. The races that remain come from one user (two tabs, fast drags, a double-click) and from users signing up with the same email. Every guard lives in Postgres, because a lock inside one Python process means nothing to the other replica.
        [svg]
      Both requests ask to place a task right after A. The shaded bars show who holds the per-user lock (pg_advisory_xact_lock on the owner id; it's released at commit). Without it, both would read a0 | a1 and both would write a0V. The unique index on (owner_id, rank) would then reject one, and the user would see an error instead of a silent tie. Other users' writes never wait for this lock.
      D16
        Order changes are serialized per user, in Postgres
locked
          ChoiceCreating a task and moving one each start their transaction with pg_advisory_xact_lock(hashtextextended(owner_id::text, 0)), then read the neighbours, compute the rank and write. A unique index on (owner_id, rank) backs it up. Edits and deletes don't take the lock, since they never change ranks.
          IsolationPostgres's default, READ COMMITTED, and that's deliberate. Each statement reads a fresh snapshot, so the neighbour read after the lock is granted sees the other move's commit. Under REPEATABLE READ the snapshot would be taken at the lock statement, before that commit, and both moves would compute the same rank.
          Instead ofAn asyncio.Lock, which only covers one process. SERIALIZABLE everywhere, which needs retry loops on every write. A version check on the whole list.
          WhyThe lock is the narrowest correct one: one user's ordering writes queue for a few milliseconds, and nothing else waits.
          TestingThe race tests run with the lead present. We watch them fail with the lock removed, then pass with it in place, before the backend PR is raised.
      D17
        Tabs stay fresh, and edits can't silently overwrite each other
locked
          The caseTab 2 loaded a task before tab 1 saved a change to it. Tab 2 then saves its stale copy, and tab 1's change is silently lost.
          ChoiceTwo layers. First, freshness: whenever a tab regains focus or the network comes back, TanStack Query refetches what's on screen. If the refetch brings a newer version of a task while the user has unsaved edits to it, the detail screen says "Changed elsewhere" straight away and offers to review or reload. Second, the guarantee: each task has an integer version, sent as an ETag. PATCH with If-Match updates only if the version still matches (UPDATE … WHERE id = :id AND owner_id = :me AND version = :v), otherwise it returns 412. The detail screen always sends If-Match. PATCH changes only the fields sent.
          Why bothRefreshing on focus prevents most mismatches but can't catch them all. It mustn't overwrite a half-typed draft, a change from another device can land while this tab keeps focus, and scripted clients have no focus at all. The version check catches everything else in one conditional UPDATE, with no locks.
         |  | Race | Guard | Test that proves it
           | Two sign-ups with one email | Unique index on email; the insert's IntegrityError becomes 409. Never check-then-insert. | Integration: 20 concurrent sign-ups, exactly one 201 and nineteen 409s
           | Moves and creates in one list at once | Per-user advisory lock, unique (owner_id, rank) | Integration: 50 concurrent moves; afterwards the ranks are unique and the list holds the same tasks. Live: the same through both replicas
           | Two tabs edit one task | Refetch on focus; "Changed elsewhere" notice; version, If-Match, 412 | Integration: two PATCHes on the same version, one 200 and one 412. Component: a newer version arriving under a draft shows the notice
           | Edit or toggle after delete | Owner-scoped UPDATE affects 0 rows → 404 | Component: a 404 on a mutation removes the row and says why
           | A late search response overwrites a newer one | Results cached per search term; superseded requests aborted with AbortSignal | Hook test: MSW delays the response for "ab" past the one for "abc", and "abc" stays on screen
           | A refetch lands on top of an optimistic reorder | cancelQueries before the optimistic write; reorder mutations share one scope, so they run in order | Component: three quick moves end in the order the user made
           | Something blocks the event loop | Async-only handlers, hashing off the loop (D13, D14) | Backend fixture: asyncio debug mode with a 50 ms slow-callback threshold; a test fails if any callback blocks longer
           | Load beyond the limits | Request, connection and hash limits; 503 with the envelope (D13 to D15) | Load test (D18): no 5xx at target load, p95 within budget
      D18
        A load test before submission
locked
          Choicek6, run from its official container as a compose profile (docker compose --profile load run k6), so nothing needs installing. 200 virtual users, each with its own account, ramp up over 1 minute and hold for 3. Each one loops: list, search, create, toggle, move, edit, delete, with 1 second of think time. After the run, a check script confirms every user's list has unique ranks and the expected number of tasks.
          PassUnder 0.1% failed requests and no 5xx. p95 latency under 250 ms for reads and under 400 ms for writes; under 1.5 s for sign-in, which queues on purpose (D14). Results are saved with the machine's specs and quoted in the README.
          Instead ofLocust, which is Python and fits the backend, but lacks k6's built-in pass/fail thresholds.
          WhyIt shows the limits in D13 to D16 working under real concurrency, and gives reviewers a script they can rerun at their own scale.
          CapacityA second, stepped run raises the number of users until a budget breaks. The last step that passed is the round's capacity figure for the final report (D15). It's repeated in rounds 2 and 3.
          Run withThe lead. Scripts and budgets are reviewed before the first run, and results are walked through together.

      D19
        Health checks: /livez and /readyz
locked
          ChoiceTwo probes at the API root, outside /api/v1. Nginx doesn't route them, so only Docker and Kubernetes reach them. Liveness checks nothing but the process. Readiness checks the database and starts failing as soon as shutdown begins.
          Instead of/health, or a single /healthz.
          WhyNo standard path exists: the IETF's health-check format never went past a draft. The trailing z is Google's convention for keeping probe paths clear of app routes. Kubernetes deprecated /healthz for its own API server in v1.16 in favour of separate /livez and /readyz, and we follow that split. Keeping them separate matters: if liveness checked the database, a short database outage would make Kubernetes restart every API pod at once, turning a blip into an outage. Readiness only takes a pod out of rotation.
    List responses are wrapped as {"items": [...]}, so a paging cursor can be added later without breaking the client. An after_id that doesn't exist and one that belongs to someone else get the same 400, so the response doesn't reveal which it was.
